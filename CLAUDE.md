# Unicorn (JS13K entry)

A trick/physics bike game built for the [js13kgames](https://js13kgames.com/) competition.
The entire zipped submission (HTML + CSS + JS) must fit under **13,312 bytes (13 KB)** —
this single constraint drives most of the build tooling and a good chunk of the code
style described below. When in doubt about *why* something looks unusual, assume it's
in service of that byte budget.

## Running it

```sh
nvm use && npm install
npm start          # watch + serve build/debug.html on http-server
npm run sizecheck   # quick preprod build + zip, prints the resulting size
```

`make build` (used in CI) produces debug, preprod, and prod builds and zips.

## Architecture

There is **no bundler and no ES modules**. `src/**/*.js` are plain scripts, everything
lives in the global scope, and `build-game.ts` concatenates them in a fixed, meaningful
order (`JS_FILES` array) before assembling `src/index.html` / `src/style.css` around the
result. If you add a new file, add it to `JS_FILES` in the right spot (dependencies
before dependents) — nothing is auto-discovered.

Runtime shape:
- `Game` (`game.js`) owns a stack of `Screen`s and drives the RAF loop.
- `World` (`model/world.js`) owns `Entity` instances in a `Set`, plus a `categories` map
  of `Set`s (e.g. `'ground'`, `'bike'`, `'camera'`) used instead of `instanceof` checks
  for querying groups of entities.
- `Entity` subclasses implement `cycle(elapsed)` (update) and `render()` (draw via the
  2D canvas context stored in the global `ctx`). `PhysicsObject` adds hitbox-based
  collision against ground segments, substepped through `cycleUnsafe` to avoid tunneling.
- Entities are object-pooled: `Entity.recycle(SomeClass)` pulls a free instance from a
  per-class pool (or constructs one) and calls `reset()`; `world.remove()` returns it to
  the pool. New pooled entity types should follow this `reset()`-instead-of-`new` pattern
  rather than allocating fresh objects every frame.
- Rendering nests `ctx.wrap(fn)` (defined in `graphics/wrap.js`) instead of manual
  `save()`/`restore()` pairs — always prefer it for scoped transforms/styles.

## Code style

- **Plain JS, no TypeScript** in `src/` (TS is used only for the build scripts,
  `build-game.ts` / `build-zip.ts`). Game code stays untyped on purpose so nothing
  constrains how aggressively it gets renamed/rewritten at build time.
- Everything is declared as an implicit/bare global: `foo = (a, b) => { ... }`,
  `class Foo { ... }`, rather than `function foo` or `export`. There's one shared global
  scope across the whole concatenated file; `globals.js` declares the handful of mutable
  globals (`can`, `ctx`, `G`, `inputMode`, ...) via a single comma-separated `let`.
- Prefer `const`/`let` semantically as normal — the build's `hardcodeConstants` step
  rewrites `const` → `let` (and `true`→`1`, `false`→`0`, `null`→`0`, `Infinity`→`999`)
  everywhere before minification, so don't hand-optimize those yourself; write normal,
  readable code and let the build do it.
- `Math.*` functions/constants (`sin`, `cos`, `atan2`, `PI`, `hypot`, `min`, `max`,
  `random`, ...) are hoisted onto `window` in `utils/math.js` and used unqualified
  (`sin(x)` not `Math.sin(x)`) in most places — this is idiomatic here, not a slip.
  (Some older files still write `Math.foo(...)` explicitly; harmless, but prefer the bare
  form in new code.)
- 4-space indentation, semicolons, trailing-comma-friendly multiline calls, arrow
  functions for free functions, `class` for entities/renderables. Getters (`get
  airborne()`) are used for derived boolean state. Comments are sparse but used
  deliberately to explain *why*, especially around the physics substep code in
  `entities/physics-object.js` — match that density, don't over- or under-comment.
- `DEBUG`, `DEBUG_INFO`, `DEBUG_COLLISIONS` are build-time flags (see below): gate
  dev-only behavior behind `if (DEBUG) ...` freely, it costs nothing in the prod build.

## Minification tricks (build-game.ts)

The build pipeline runs, in order: constant hardcoding → macro expansion → identifier
mangling → Terser → Roadroller → HTML/CSS minification → template assembly. Debug builds
skip mangle/minify/roadroll entirely so stack traces and `F12` stay readable.

- **Constant hardcoding** (`hardcodeConstants`): textually replaces named constants
  (`DEBUG`, `INPUT_MODE_*`, the `Z_*` render-order constants generated by an incrementing
  loop, `true`/`false`/`const`/`null`/`Infinity`) with literal values before anything else
  runs, so Terser can dead-code-eliminate `if (DEBUG)` branches in prod.
- **`nomangle(expr)`** — a build-time macro (from `@remvst/js13k-tools`) that shields an
  expression from the custom mangler, e.g. `nomangle(g)` in `index.js` (see below) or
  `ctx.textAlign = nomangle('left')` where the string must stay exactly `'left'` for the
  Canvas API. Wrap anything whose exact spelling an external API depends on.
- **`evaluate(expr)`** — runs `expr` at *build* time via `eval` and inlines the result
  literal into the output. Used for precomputing constant data.
- **Implicit DOM globals**: `<canvas id=g>` means `g` is directly readable as a bare
  global (`window.g`) per HTML spec — `index.js` does `can = nomangle(g)` instead of
  `document.getElementById('g')`. Element/ids are kept to a single letter for this reason.
- **Custom identifier mangler** (`mangle()`): renames identifiers project-wide by usage
  frequency (most-used names get the shortest replacements), independent of and prior to
  Terser's own mangler (which is run with `properties: false` — property names are
  handled by our mangler, not Terser's, to give the `force`/`skip` lists control).
  `MANGLE_PARAMS.force` in `build-game.ts` explicitly enrolls common property names
  (`x`, `y`, `color`, `angle`, `update`, ...) that Terser wouldn't otherwise touch;
  `.skip` excludes specific names that must survive (e.g. `repeat`). When adding a new,
  frequently-used property name to a hot class, consider adding it to `force`.
- **Roadroller** packs the post-Terser JS into a compressed self-decoding blob — the
  single biggest size lever, applied at `--roadroll-level=1` for preprod (faster to
  build) and `=2` for prod (max compression). It's opaque, so don't try to
  read/debug roadrolled output — always work against a debug or preprod build.
- **HTML/CSS**: `html-minifier` and `clean-css` shrink `index.html`/`style.css` before
  they're spliced into the JS via `assembleHtml`'s `{{{ CSS_INJECTION_SITE }}}` /
  `{{{ JS_INJECTION_SITE }}}` placeholders. Keep markup/CSS terse (short ids like `#g`,
  `#t`) since every extra byte there counts too.
- **Final packaging** (`build-zip.ts`): zips the built HTML, then runs `advzip
  --shrink-insane` and the vendored Efficient-Compression-Tool (`ect -zip -9 -strip`) for
  extra deflate savings, checking the result against the 13 KB cap after each step via
  `logFileSize`.

## When adding code

- Ask whether new state/behavior belongs on an existing `Entity` category or needs a new
  one; prefer categories over new base classes where possible.
- Keep hot-path property names short and add them to `MANGLE_PARAMS.force` if they'll
  appear often, otherwise the custom mangler under-prioritizes them.
- Don't add real modules/imports — stick to global-scope files + `JS_FILES` ordering.
- Verify size impact with `npm run sizecheck` for anything nontrivial; the 13 KB limit is
  hard, not aspirational.
